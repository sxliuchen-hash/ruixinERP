# 主项目统一权限与 SSO 联调确认回填表

> 本表为 R7 之前的历史版本，已停止回填。当前请使用 `docs/2026-07-11-主项目统一权限与SSO联调待确认回填表-R7.docx`；state 已锁定为 ERP 发起并绑定浏览器，不再是可选项。

## 1. 使用说明

请主项目团队直接在每个表格的“主项目回复”列填写结果，然后把本文件反馈给 ERP 团队。

ERP 已对主项目当前统一应用权限改造分支做过只读预审。代码现状、可复用基础和当前差距见：

```text
docs/2026-07-10-主项目现状只读预审与ERP改造差距清单.md
```

回复规则：

- 已确认：填写最终值或“接受 ERP 推荐方案”。
- 暂未确定：填写“待定 + 负责人 + 预计确认日期”。
- 需要调整：填写调整后的接口、字段或规则，并说明原因。
- Client Secret、私钥等敏感值不要写入本文，只填写凭证编号、保管人和安全交付方式。
- “哪些角色拥有具体业务权限”由业务负责人决定；主项目技术团队只需确认权限中心能否配置和下发。

## 2. ERP 已锁定的契约

以下内容是 ERP 当前正式实现，主项目联调应以此为基准：

| 项目 | ERP 已实现值 |
| --- | --- |
| 权限目录 | Manifest v1.3.0，117 个权限、192 条接口映射 |
| 权限编码 | `erp.<module>.<action>` |
| ERP 入口权限 | `erp.app.view`，只支持 `all` scope |
| 永久用户标识 | 主项目 `users.id`，对应 assertion `sub` |
| 生产回调 | 生产部署必须显式配置并锁定为 `https://erp.iptt.top/sso/callback`；代码在 production 不提供回调默认值 |
| ERP 浏览器兑换接口 | `POST https://erp.iptt.top/api/v1/auth/sso/exchange`，Body 为 `{ "code": "..." }` |
| audience | `erp` |
| assertion 算法 | RS256，必须带有效 `kid` |
| assertion 防重放 | 每个 assertion 必须使用全局唯一 `jti`；ERP 会原子消费 `jti`，同一 assertion 第二次使用会被拒绝；生产环境防重放依赖 Redis，异常时 fail-closed |
| assertion issuer 默认值 | `patent-notice-system` |
| ERP 会话 | `main_sso` 短会话默认 2 小时；灰度期 legacy 密码会话仍按 `JWT_EXPIRES_IN`，默认 7 天 |
| 普通权限版本缓存 | 默认 120 秒，最大不超过 5 分钟 |
| team scope 缓存 | 默认 120 秒，最大不超过 5 分钟；重新 SSO 或发现版本不一致时主动清除 |
| 高风险权限版本 | 每次实时查询主项目，失败时默认拒绝 |
| 文件下载 | Authorization Header 或 60 秒一次性 Ticket，不接受 `?token=`；Ticket 绑定用户、权限版本、资源 ID，并再次执行资源 scope 和附件 key 归属校验 |
| 业务 API 目标模式 | 最终使用 `IP_AUTH_MODE=client_credentials`；SSO 灰度期使用 `hybrid` 分流 main_sso/legacy；只有显式设置 `legacy_shared_jwt` 才进入全量旧认证应急回滚 |

正式 Manifest：

```text
backend/src/permissions/erp-permission-manifest.json
```

主项目拉取 Manifest 的 ERP 接口：

```http
GET https://erp.iptt.top/api/v1/internal/permissions/manifest
X-ERP-Manifest-Client-Id: <id>
X-ERP-Manifest-Client-Secret: <secret>
```

四套凭证方向必须分离：

| 凭证 | 调用方向 | 用途 |
| --- | --- | --- |
| `ERP_SSO_CLIENT_ID/SECRET` | ERP 后端 → 主项目 | 一次性 Code 兑换 |
| `MAIN_API_CLIENT_ID/SECRET` | ERP 后端 → 主项目 | team scope、permissionVersion、专利业务 API |
| `ERP_MANIFEST_CLIENT_ID/SECRET` | 主项目 → ERP 后端 | 拉取 ERP Manifest |
| `ERP_PROVISION_CLIENT_ID/SECRET` | 主项目 → ERP 后端 | 绑定账号时幂等创建/同步 Employee |

四套凭证不能共用同一组 ID/Secret，也不能与浏览器用户 Token 混用。

## 4. SSO Code 与兑换接口

### 4.1 主项目把浏览器送到 ERP

R7 流程要求主项目入口先打开 ERP `/sso/initiate`。ERP 生成并绑定浏览器 state，主项目 authorize 生成 Code 后必须把浏览器送到：

```text
GET https://erp.iptt.top/sso/callback?code=<URL编码后的一次性Code>&state=<ERP生成的state>
```

ERP 前端读取 `code/state` 后立即清除 URL/history，随后在浏览器内调用：

```http
POST /api/v1/auth/sso/exchange
Content-Type: application/json

{ "code": "一次性Code", "state": "与当前浏览器Cookie绑定的state" }
```

主项目 authorize 返回服务端生成的固定 `redirectUrl`，其中只允许 `code/state`；主项目不得允许浏览器传入任意回调地址，也不得在响应中单独暴露可由前端重新拼接的 Code/state。不得使用 `token`、`redirect` 或其他长效凭证参数。

### 4.2 ERP 调用主项目的请求

ERP 当前默认发送：

```http
POST /api/v1/internal/sso/erp/exchange
X-ERP-Client-Id: <ERP_SSO_CLIENT_ID>
X-ERP-Client-Secret: <ERP_SSO_CLIENT_SECRET>
Content-Type: application/json

{
  "authorizationCode": "一次性Code",
  "state": "ERP生成并绑定当前浏览器的state",
  "audience": "erp",
  "redirectUri": "https://erp.iptt.top/sso/callback"
}
```

请确认：

| 编号 | 确认项 | ERP 推荐值或要求 | 主项目回复 |
| --- | --- | --- | --- |
| SSO-01 | 是否接受以上 Header 名称 | `X-ERP-Client-Id`、`X-ERP-Client-Secret` | 【待填写】 |
| SSO-02 | 是否接受以上 JSON 字段名 | `authorizationCode/state/audience/redirectUri` | 【待填写】 |
| SSO-03 | Code 随机长度 | 至少 128 bit；建议 32 字节随机值 | 【待填写】 |
| SSO-04 | Code 存储和消费方式 | Redis 只保存 Code 哈希；使用 `GETDEL` 或等价事务原子消费，重放返回失败 | 【待填写】 |
| SSO-05 | 兑换时是否重新检查用户状态 | 必须检查用户未禁用、未离职 | 【待填写】 |
| SSO-06 | 兑换时是否重新检查入口权限 | 必须再次检查 `erp.app.view` | 【待填写】 |
| SSO-07 | redirectUri 校验 | 必须与 Code 绑定的固定回调完全一致 | 【待填写】 |
| SSO-08 | audience 校验 | 固定为 `erp` | 【待填写】 |
| SSO-09 | 已消费/过期 Code 的状态码 | 建议 400/409/410；ERP 均按无效 Code 处理 | 【待填写】 |
| SSO-10 | 无 ERP 权限的状态码 | 建议 403 | 【待填写】 |
| SSO-11 | 限流状态码 | 建议 429 | 【待填写】 |

### 4.3 主项目返回值

ERP 接受以下响应包裹形式：

```json
{
  "success": true,
  "data": {
    "assertion": "<RS256 JWT>"
  }
}
```

也接受主项目现行统一格式 `{ "code": 200, "message": "兑换成功", "data": { "assertion": "..." } }`，或直接返回 `{ "assertion": "..." }`。

| 编号 | 确认项 | ERP 推荐值或要求 | 主项目回复 |
| --- | --- | --- | --- |
| SSO-12 | 响应是否按上述格式返回 | 推荐 `success + data.assertion` | 【待填写】 |
| SSO-13 | assertion 有效期 | 建议 60～120 秒，仅用于服务端兑换 | 【待填写】 |
| SSO-14 | assertion 是否每次使用唯一 `jti` | 必须全局唯一，长度 8～200；ERP 会原子消费，同一 assertion 或同一 `jti` 第二次使用会返回认证失败 | 【待填写】 |
| SSO-15 | 主项目是否记录 Code 和 assertion 审计 | 记录 userId、jti、clientId、结果，不记录完整凭证 | 【待填写】 |
| SSO-16 | assertion 重复签发策略 | 每次成功兑换 Code 必须新签发 assertion；不得缓存后向多个 Code 返回同一 assertion | 【待填写】 |

## 5. assertion 字段与签名

主项目 assertion 必须包含：

```text
Header: alg=RS256, kid=<密钥编号>
iss=patent-notice-system
aud=erp
sub=<users.id 的十进制字符串>
iat, exp, jti
user.id（数值必须与 sub 相同）
user.username
user.role
permissions
permissionVersion
```

正式格式使用嵌套 `user` 对象。ERP 为旧联调兼容，也能读取顶层 `username/role/realName`，但主项目新实现不要使用该兼容格式。

权限结构：

```json
{
  "erp.app.view": { "allowed": true, "scope": "all" },
  "erp.contract.view": { "allowed": true, "scope": "team" }
}
```

| 编号 | 确认项 | ERP 推荐值或要求 | 主项目回复 |
| --- | --- | --- | --- |
| JWT-01 | `sub` 是否永久使用 `users.id` | 必须是无前导零的正整数十进制字符串；数值类型会被 ERP 拒绝 | 【待填写】 |
| JWT-02 | `user.id` 与 `sub` 的一致性 | 必须满足 `Number(user.id) === Number(sub)`，否则 ERP 返回 401 | 【待填写】 |
| JWT-03 | `user.username` 和 `user.role` 是否始终存在 | ERP 当前要求二者都存在；role 不用于决定细粒度权限 | 【待填写】 |
| JWT-04 | 是否接受嵌套 `user` 为正式唯一格式 | 推荐确认；顶层用户字段只保留兼容读取 | 【待填写】 |
| JWT-05 | `permissions` 是否只返回已允许项 | 推荐只返回 `allowed=true` 项 | 【待填写】 |
| JWT-06 | scope 枚举 | 只能是 `self/team/all`，且必须受 Manifest 支持范围约束 | 【待填写】 |
| JWT-07 | `permissionVersion` 类型 | 非负整数 | 【待填写】 |
| JWT-08 | 是否确认只使用 RS256 | ERP 当前不接受 HS256/ES256 assertion | 【待填写】 |
| JWT-09 | active/previous 公钥并存时间 | 至少覆盖旧 assertion 最大有效期 | 【待填写】 |
| JWT-10 | 公钥轮换负责人 | 填写姓名或团队 | 【待填写】 |
| JWT-11 | 密钥泄漏应急流程 | 更换 `kid`、发布新公钥、停用旧私钥、审计 jti | 【待填写】 |
| JWT-12 | `iat/exp` 类型和时序 | 必须为整数，`exp > iat`，默认最大生命周期 120 秒（ERP 可配置范围 30～300 秒），`iat` 不得超前 ERP 时间 5 秒以上 | 【待填写】 |
| JWT-13 | `kid` 格式 | 必须是 1～128 位非空字符串；active `kid` 必须有对应公钥，previous `kid` 与 previous 公钥必须成对配置 | 【待填写】 |

| PERM-11 | 业务授权矩阵由谁提供 | 填写业务负责人；技术团队不自行决定 | 【待填写】 |

主项目需要确认权限中心可以表达以下授权，而不是确认具体业务结果：

- 某角色能否进入 ERP。
- 某角色拥有哪些页面和操作权限。
- 同一个权限配置 `self/team/all` 中的一个范围。
- 新增权限默认拒绝。
- 权限调整后旧 ERP 会话失效。

| VER-06 | 主项目“退出全部设备” | 必须递增版本 | 【待填写】 |
