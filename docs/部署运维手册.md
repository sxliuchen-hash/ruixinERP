## 三、部署流程

### 旧一键部署入口（宝塔模式，本批版本禁止使用）

> 该历史入口已永久改为 fail-closed 拒绝桩。无论是否传参，脚本只输出本手册路径并以状态码 `78` 退出，不执行拉取、DDL、依赖安装、构建、文件替换、Nginx、PM2、HTTP 检查或流量切换。正式发布必须使用后文“增量更新（含迁移）一条龙”的手工维护流程。

服务器上执行：

```bash
bash /var/www/erp/backend/scripts/deploy.sh
```

执行上述命令只会得到拒绝信息和非零状态码，不会改变服务器状态。首次接入 SSO 前，仍必须先按下文 Nginx 配置章节更新宝塔站点配置；响应头烟雾检查不能替代停写、备份恢复和 ready 门禁。

### 旧一键部署入口（仓库 Nginx 模板模式，本批版本禁止使用）

该入口与宝塔模式入口使用相同的 fail-closed 拒绝契约；以下命令仅用于验证拒绝行为，不得作为发布命令：

```bash
bash /var/www/erp/deploy/deploy.sh
```

脚本不会安装 `deploy/nginx.conf`、不会改动 `/etc/nginx`，也不会启动或重启任何服务。需要使用仓库 Nginx 模板时，按下文手工维护发布流程执行并逐项验收。

### 旧手动步骤参考（仅限无数据库结构变化的历史版本）

> 下列简化步骤不包含维护停写、同一备份工件恢复和生产 preflight，不适用于本批版本。当前正式步骤以“增量更新（含迁移）一条龙”为准。

```bash
# 1. 拉代码
cd /var/www/erp && git pull

# 2. 安装后端依赖（如有新依赖）
cd /var/www/erp/backend && npm install --production

# 3. 数据库迁移（如本次提交带 SQL 脚本）
mysql -u erp_db -p erp_db < /var/www/erp/backend/scripts/<迁移脚本>.sql

# 4. 构建前端
cd /var/www/erp/frontend
cp .env.production.example .env.production
# 编辑 .env.production，将 VITE_MAIN_SYSTEM_URL 改为已确认的主项目真实 Origin；
# 示例/占位域、路径、查询参数或缺失配置都会被 production build 门禁拒绝。
npm install && npm run build

# 5. 部署前端到 Nginx 目录（不能跳过！）
rm -rf /www/wwwroot/erp.iptt.top/*
cp -r /var/www/erp/frontend/dist/* /www/wwwroot/erp.iptt.top/

# 6. 重启后端
pm2 restart erp-backend

# 7. 浏览器强刷（Ctrl+Shift+R）
```

### 数据库全量备份到独立 COS 桶

正式备份不得复用应用数据库账号或 ERP 业务 COS 桶。先由数据库管理员创建独立只读账号，权限仅允许备份所需的
`SELECT`、`SHOW VIEW`、`TRIGGER`、`EVENT` 和版本所需的只读存储过程查看权限；不得授予
`INSERT/UPDATE/DELETE/CREATE/DROP/ALTER/INDEX`。同时创建独立备份桶和只允许该桶上传、HEAD 的凭证。

受控环境至少配置：

```dotenv
DB_BACKUP_HOST=127.0.0.1
DB_BACKUP_PORT=3306
DB_BACKUP_NAME=erp_db
DB_BACKUP_USER=erp_backup_readonly
DB_BACKUP_PASSWORD=<只读备份密码>
BACKUP_DIR=/var/backups/erp
BACKUP_LOCK_FILE=/var/backups/erp/.backup.lock
KEEP_DAYS=30

COS_BACKUP_SECRET_ID=<独立备份凭证>
COS_BACKUP_SECRET_KEY=<独立备份密钥>
COS_BACKUP_BUCKET=<独立备份桶>
COS_BACKUP_REGION=<备份桶地域>
```

`DB_BACKUP_USER` 与应用 `DB_USER` 相同、或 `COS_BACKUP_BUCKET` 与业务 `COS_BUCKET` 相同时，脚本会拒绝执行。

```bash
cd /var/www/erp/backend
bash -n scripts/backup-to-cos.sh
bash scripts/backup-to-cos.sh
```

脚本使用 `flock` 防止并发执行；dump 先写入权限受限的 `.part`，通过非空检查、`gzip -t` 和 SHA256 后才原子改名。
上传时写入 `x-cos-meta-sha256`，随后通过 COS HEAD 校验对象长度和 SHA256 元数据。HEAD 成功后，在
`BACKUP_DIR` 内原子写入权限为 `0600` 的 `<artifact>.receipt.json`，记录随机 `backupId`、生成时间、源库
`server_uuid`、工件绝对路径/大小/SHA256、固定 dump profile，以及 COS bucket/region/精确 objectKey/HEAD 元数据、
ETag、versionId 和上传 SecretId 的 SHA256 指纹（不记录 SecretId 明文或 SecretKey）。脚本最后一行输出脱敏 JSON，
其中 `receiptPath` 是恢复 smoke 唯一允许的输入。退出时只清理本次
MySQL 临时凭证文件和未完成的 `.part`；按 `KEEP_DAYS` 清理时工件、SHA sidecar 和 receipt 使用相同保留期。

该流程证明“本地备份工件已生成、同一字节摘要已上传且当时的远端 HEAD 一致”。任何生产迁移前还必须使用该精确
receipt 运行隔离恢复 smoke，不能重新生成另一份 dump。
在维护窗口前预拉取并记录与源库兼容、固定 digest 的 MySQL 镜像；维护窗口内不得临时拉取：

```dotenv
ALLOW_DB_RESTORE_SMOKE=YES
DB_RESTORE_ARTIFACT_SOURCE=local
BACKUP_DIR=/var/backups/erp
DB_RESTORE_RECEIPT_PATH=/var/backups/erp/erp_db_YYYYMMDD_HHMMSS.sql.gz.receipt.json
DB_RESTORE_MYSQL_IMAGE=mysql:8.4.0@sha256:<经审核的64位digest>
DB_RESTORE_COMMAND_TIMEOUT_MS=300000
```

```bash
cd /var/www/erp/backend
ALLOW_DB_RESTORE_SMOKE=YES \
DB_RESTORE_ARTIFACT_SOURCE=local \
BACKUP_DIR=/var/backups/erp \
DB_RESTORE_RECEIPT_PATH=/var/backups/erp/erp_db_YYYYMMDD_HHMMSS.sql.gz.receipt.json \
npm run smoke:db-restore
```

恢复 smoke 必须显式接收单个精确 `DB_RESTORE_RECEIPT_PATH`。该路径必须是 `BACKUP_DIR` 内固定命名的直属文件，
禁止 `latest`、`list`、通配符、`..`、目录扫描和桶列表。receipt 与工件必须都是非符号链接普通文件；Linux 生产
环境下目录禁止组/其他用户访问，两个文件权限必须为 `0600`。脚本重新校验工件大小、gzip 完整性和 SHA256，并在
实际恢复字节流上再次计算同一 SHA256；源码不会调用 dump 命令生成第二份工件。receipt 对应 dump 的 SQL 仍经过
流式危险语句扫描。

恢复 smoke 只读取同一套 `DB_BACKUP_*` 源库配置，不接受任何目标 host、port 或 database。它校验当前源库
`server_uuid` 与 receipt 一致，并保留源库只读快照和行数比对，然后自行创建随机命名、
`--network none --pull never`、无端口映射和无宿主数据卷的临时 MySQL 容器；校验源账号权限只作用于指定 ERP 库，
源/目标 `server_uuid` 不同，dump 中不存在 `CREATE/DROP DATABASE`、`USE`、`CREATE USER`、`GRANT`、`SET GLOBAL`，
并精确比较表/视图、全表行数、列、索引、约束、触发器、存储过程和事件。五项关键唯一索引、
`confirmed_period_key` STORED 生成列以及 `payments.account_id` 可空必须全部通过。

成功时只输出脱敏 JSON 摘要，退出码 `0`；配置、源账号权限、工件、恢复、验证、清理分别使用非零分层退出码。
`finally` 只按本次保存的完整容器 ID 执行 `docker rm -f`，并精确清除本次 0700 临时目录。完成后立即把
`ALLOW_DB_RESTORE_SMOKE` 恢复为 `NO`。不得通过列举桶对象后猜测 `latest`，也不得为脚本增加任何外部恢复目标地址。

`DB_RESTORE_ARTIFACT_SOURCE=local` 是同机迁移门禁：恢复 receipt 对应的本地 artifact，不需要 COS 读取权限。

正式远端灾备模式使用 `DB_RESTORE_ARTIFACT_SOURCE=cos`。该模式仍显式接收同一个精确 receipt，但不要求本地 artifact
存在；只使用独立只读 `COS_BACKUP_RESTORE_SECRET_ID/SECRET_KEY`（临时凭证可另配
`COS_BACKUP_RESTORE_SECURITY_TOKEN`），按 receipt 中精确 bucket/region/objectKey 和可选 versionId 执行一次
`GetObject`。有 ETag 时同时发送 `IfMatch`，禁止 `ListObjects`、`ListVersions`、`latest` 和任何桶枚举。下载内容流式写入
本次 `0700` 临时目录中的 `0600` 文件，重新校验 size/gzip/SHA256 后再恢复，最终随临时目录精确清理。

远端恢复凭证不得复用日常 `COS_BACKUP_SECRET_ID/SECRET_KEY`。即使灾备环境未保留上传凭证，脚本也会比较 restore
SecretId 的 SHA256 与 receipt 中的上传凭证指纹并 fail-closed。日常上传凭证不增加 GetObject 权限，灾备凭证只授予
指定备份桶的只读 GetObject 权限。

远端灾备演练示例：

```bash
ALLOW_DB_RESTORE_SMOKE=YES \
DB_RESTORE_ARTIFACT_SOURCE=cos \
BACKUP_DIR=/var/backups/erp \
DB_RESTORE_RECEIPT_PATH=/var/backups/erp/erp_db_YYYYMMDD_HHMMSS.sql.gz.receipt.json \
COS_BACKUP_RESTORE_SECRET_ID=<独立只读SecretId> \
COS_BACKUP_RESTORE_SECRET_KEY=<独立只读SecretKey> \
npm run smoke:db-restore
```

### Nginx 配置

位置：`/www/server/panel/vhost/nginx/erp.iptt.top.conf`

关键配置：
- `root /www/wwwroot/erp.iptt.top;` — 前端静态文件
- `/api/` 反向代理到 `http://127.0.0.1:3001`
- SPA 路由 `try_files $uri $uri/ /index.html;`
- `/sso/callback` 必须单独返回 SPA `index.html`，设置 `Cache-Control: no-store`、`Referrer-Policy: no-referrer`，并关闭该 location 的 access log，避免查询串中的一次性 Code 落盘

生产配置至少应包含以下内容。宝塔实际站点配置与仓库
`deploy/nginx.conf` 必须保持等价：

```nginx
root /www/wwwroot/erp.iptt.top;
index index.html;

# 主项目 authorize 会跳转到 /sso/callback?code=...&state=...，必须支持 history fallback。
location = /sso/callback {
    try_files $uri $uri/ /index.html;
    access_log off;
    add_header Cache-Control "no-store, no-cache, must-revalidate, proxy-revalidate, max-age=0" always;
    add_header Pragma "no-cache" always;
    add_header Expires "0" always;
    add_header Referrer-Policy "no-referrer" always;
}

location / {
    try_files $uri $uri/ /index.html;
}

location /api/ {
    proxy_pass http://127.0.0.1:3001;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

> 不要让 `/sso/callback` 继承默认 combined access log。默认日志格式包含完整请求 URI，
> 会把查询串写入日志。若未来需要保留回调访问审计，必须改用明确剔除 `$args` 的专用日志格式，
> 不得记录真实 Code。

> 仓库 `deploy/nginx.conf` 直接以 `/var/www/erp/frontend/dist` 为 root；
> 宝塔部署以 `/www/wwwroot/erp.iptt.top` 为 root。二者只能选择与实际发布流程一致的一种，
> 但 SPA fallback、API 反代和 SSO 回调安全头必须一致。

## 七、常见故障排查

### 问题 1：前端代码改了但页面没变化

**原因**：前端构建后没拷贝到 Nginx 服务目录。

**解决**：
```bash
ls -la /www/wwwroot/erp.iptt.top/index.html  # 确认时间是不是最新的
cp -r /var/www/erp/frontend/dist/* /www/wwwroot/erp.iptt.top/
# 浏览器 Ctrl+Shift+R 强刷
```

### 问题 2：服务启动失败

```bash
pm2 logs erp-backend --err --lines 50  # 看错误日志
tail -100 /var/www/erp/backend/logs/error.log
```

常见原因：
- 数据库连接失败：检查 `.env` 中 `DB_PASSWORD` 等
- 端口被占用：`lsof -i:3001`
- 缺少新依赖：`cd /var/www/erp/backend && npm install`

### 问题 3：定时任务没运行

确认日志里有注册信息：
```bash
grep "已注册" /var/www/erp/backend/logs/app.log | tail -10
```

### 问题 4：express-rate-limit 报 X-Forwarded-For 警告

已修复（`app.set('trust proxy', 1)`）。如再出现，确认 `backend/src/app.js` 中有该配置。

### 问题 5：调用 IP 系统 401

IP_API_CLIENT_ID=<ERP服务账号>
IP_API_CLIENT_SECRET=<ERP服务密钥>

> `scripts/sync-tables.js` 含 Sequelize `alter:true`，仅允许本地开发库使用；脚本在 `NODE_ENV=production` 会直接拒绝，禁止将其加入生产部署或恢复流程。
> 安全相关：文件下载一次性票据依赖 Redis；Redis 不可用时票据签发失败，不允许降级回 URL 长效 Token。如跨域访问，确保 `.env` 的 `CORS_ORIGIN` 配置正确（同源经 Nginx 反代不受影响）。

`npm run precheck:release` 只执行读取和连接检查：验证当前仓库根、发布单完整 Commit、clean tree、受 Commit 跟踪的
`deploy/nginx.conf` 安全契约、固定前置命令、Docker daemon、已预拉取的固定 digest 恢复镜像、`BACKUP_DIR` 可用空间，
并复用统一认证 preflight 只读检查配置、数据库结构和 Redis。它只执行 `docker info` 和 `docker image inspect`，不会拉取镜像。
它不会执行 `git pull`、文件写入、DDL、PM2、Nginx reload、停启服务或流量切换。本机开发单测可显式传
`--allow-dirty-development`，但该参数在 `NODE_ENV=production` 下会直接失败，不能作为发布绕过项。

`npm run wait:ready` 只轮询固定路径 `/api/v1/health/ready`，总超时、轮询间隔和单请求超时都有上限；URL
不得包含 userinfo、query、fragment、Token 或 Code。本机 `localhost/127.0.0.1/::1` 可使用 HTTP；远程探针必须使用
HTTPS，并通过 `READY_ALLOWED_HOSTS=erp.iptt.top` 或重复的 `--allow-host` 提供精确白名单（不支持通配符）。工具禁止重定向，
且只有 HTTP 200 以及 `success=true`、`code=READY`、`data.ready=true` 同时满足才记为一次成功；至少连续 3 次成功才通过，
任何一次失败都会把连续计数清零。超时或响应不合约时保持维护模式。

### 维护发布失败处理

进入维护模式后，任何阶段失败都必须保持维护页和停写状态，记录失败命令、Commit、receipt `backupId`、操作人和时间，再按下表处理。不得因脚本“可重跑”而直接恢复流量；MySQL DDL 可能已经隐式提交。

| 失败阶段 | 必须动作 | 恢复流量条件 |
| --- | --- | --- |
| 只读 release precheck 失败 | 不进入维护模式、不执行备份或迁移；修复 Commit、工作树、工具、磁盘、candidate、配置、DB 或 Redis | 使用同一发布单完整 Commit 重跑并全部通过 |
| 备份或 COS 校验失败 | 停止发布，不执行任何迁移；保留旧服务版本 | 重新生成备份且 receipt、Put/HEAD 全部成功 |
| 本地或 COS 恢复 smoke 失败 | 停止发布，保留精确 receipt 和失败日志；禁止换成 `latest` | 同一 receipt 指定工件恢复及结构/行数校验通过 |
| 任一迁移失败 | 停止后续迁移和启动；记录已执行语句，按具体迁移做前滚修复或经审批恢复旧库 | 数据库结构人工复核、全部迁移幂等重跑和 preflight 通过 |
| production preflight 失败 | 不启动新版，不恢复流量 | 配置、数据库和 Redis 问题修复后 preflight 通过 |
| 前端构建或部署失败 | 保持旧前端或从已校验旧制品恢复；禁止留下空目录/半套文件 | 完整新制品部署且 Nginx candidate 检查通过 |
| PM2 启动或 ready 超时 | 保持维护模式；使用 `pm2 logs --nostream` 取证，禁止仅凭 `pm2 status` 放流 | ready 连续通过并由发布负责人签字 |
| Nginx reload 或 SSO 路由检查失败 | 保持维护模式，恢复上一份已验证 Nginx 配置 | `nginx -t`、ready、SSO initiate/callback 和安全响应头均通过 |

维护模式退出必须同时满足：后台任务已恢复、ready 通过、Nginx 检查通过、关键只读业务 smoke 通过，并由发布负责人明确记录“允许恢复流量”。

### 进程启动门禁与健康探针

- `node src/app.js`、`npm start` 和 PM2 直接启动都会在连接数据库、Redis、启动后台任务和监听端口之前执行生产运行配置门禁；配置不合格时进程以退出码 1 结束。
- 完整 `npm run preflight:unified-auth` 用于正式发布，仍要求 `ENABLE_SSO_LOGIN=true` 并执行 Redis/可选数据库检查。
- `npm run precheck:release` 是进入维护模式前的只读总门禁；迁移完成后仍必须再次执行 `npm run preflight:unified-auth`，不能用迁移前结果代替迁移后结构复核。
- 生产运行门禁允许已记录审批的应急回滚组合：`ENABLE_SSO_LOGIN=false`、`ENABLE_PASSWORD_LOGIN=true`、`ENABLE_LEGACY_SESSION=true`；不得关闭全部登录入口，也不得在关闭 legacy session 时保留密码登录。
- `/api/v1/health/live` 只检查进程是否可响应。
- `/api/v1/health/ready` 检查本地配置、ERP 数据库和当前功能所需 Redis；返回 503 时负载均衡器不得继续导入新流量。该探针不会调用主项目远程接口。
- `npm run wait:ready` 对该固定契约执行有界轮询；失败只返回安全错误码/状态，不输出响应正文或 URL 凭证。
- Nginx 只将连接类 502/504 收敛为通用 503 JSON；ERP 后端主动返回的业务 503（例如 `MAIN_TEAM_SCOPE_UNAVAILABLE`）必须原样透传。

## 十、统一认证生产配置预检

后端启动或 PM2 重启前必须执行；正式部署应同时复核数据库业务唯一约束：

```bash
cd /var/www/erp/backend
UNIFIED_AUTH_PREFLIGHT_CHECK_DB=true UNIFIED_AUTH_PREFLIGHT_CHECK_REDIS=true NODE_ENV=production npm run preflight:unified-auth
```

预检只输出检查项、Manifest 版本和安全错误，不输出 Client Secret、会话密钥或 PEM 公钥内容。它会检查：

- SSO、密码登录、legacy session 开关组合是否可用。
- 三项认证开关是否显式配置且使用合法布尔值。
- `MAIN_SSO_BASE_URL`、`MAIN_SYSTEM_URL`、`IP_API_BASE_URL` 是否显式配置为安全 URL，
  team scope 和 permissionVersion 路径是否保留 `:userId` 占位符。
- 生产 SSO callback 是否为有效 HTTPS 地址。
- `ERP_SESSION_SECRET` 是否已独立配置。
- SSO Code 兑换、主项目业务 API、Manifest 同步、Employee 建档四套 Client ID/Secret 是否完整且相互分离。
- `IP_API_CLIENT_ID/SECRET` 是否成对配置；两项均缺省时才允许整体复用 `MAIN_API`。
- RS256 active/previous `kid` 和公钥是否完整、可解析且适合轮换。
- Manifest 版本、权限编码和接口 route 是否存在重复。

手工诊断时可不设置该变量，使预检不连接数据库；正式部署脚本始终设置为 `true`。
需要单独只读检查 `employees.user_id` 唯一索引时运行：

```bash
UNIFIED_AUTH_PREFLIGHT_CHECK_DB=true UNIFIED_AUTH_PREFLIGHT_CHECK_REDIS=true NODE_ENV=production npm run preflight:unified-auth
```

数据库检查只执行认证和 `SHOW INDEX`，不会创建、删除或修复数据。缺少索引时先执行：

```bash
npm run migrate:employee-user-id-unique
npm run migrate:wechat-sp-no-unique
npm run migrate:performance-confirmed-period-unique

npm run migrate:system-settings
```

这些安全迁移会先检查重复绑定、审批单号、已确认业绩年月及系统设置既有结构；发现冲突时中止并要求人工处理，不会静默删除或覆盖数据。

## 十一、COS 测试桶单对象回环验证

该检查只验证一套独立 COS 测试桶的上传、元数据读取、下载完整性和删除能力，不读取或修改 ERP 业务桶。脚本固定生成
`erp-smoke/cos-roundtrip/` 前缀下的随机单对象，不接受外部 Key，不调用对象列表、批量删除或递归删除接口；无论中途成功或失败，
都会在 `finally` 中再次精确删除本次 Key 并确认对象不存在。

### 凭证和测试桶准备

- 单独创建测试桶，桶名必须包含 `test`、`ci`、`sandbox` 或 `smoke`，且不得等于生产 `COS_BUCKET`。
- 使用独立的短期凭证，权限仅覆盖该测试桶的 `PutObject`、`HeadObject`、`GetObject`、`DeleteObject`；不要授予列桶、删桶或生产桶权限。
- `COS_SMOKE_SECRET_ID`、`COS_SMOKE_SECRET_KEY`、可选 `COS_SMOKE_SECURITY_TOKEN` 只通过服务器密钥系统或受保护任务临时注入，不写入仓库、命令历史和工单正文。
- 普通 PR/CI 只运行 Mock Jest 测试；真实桶检查只能由运维人员手工执行，或放在带环境审批的受保护 `workflow_dispatch` 中。

### 执行

由密钥管理系统把独立变量临时写入权限为 `600` 的 `/run/secrets/erp-cos-smoke.env`；文件还需包含非敏感的真实
`COS_BUCKET` 名称供脚本做不相等校验，但不需要业务桶凭证。随后执行以下命令，避免真实 Secret 进入 shell history：

```bash
cd /var/www/erp/backend
test "$(stat -c '%a' /run/secrets/erp-cos-smoke.env)" = "600"
set -a
. /run/secrets/erp-cos-smoke.env
set +a
npm run smoke:cos-roundtrip
unset COS_SMOKE_SECRET_ID COS_SMOKE_SECRET_KEY COS_SMOKE_SECURITY_TOKEN
unset COS_SMOKE_BUCKET COS_SMOKE_REGION COS_SMOKE_TIMEOUT_MS
```

受控文件包含 `COS_SMOKE_SECRET_ID`、`COS_SMOKE_SECRET_KEY`、可选 `COS_SMOKE_SECURITY_TOKEN`、`COS_SMOKE_BUCKET`、
`COS_SMOKE_REGION`、`COS_SMOKE_TIMEOUT_MS=15000` 和 `COS_BUCKET=<真实业务桶名>`。执行后立即删除该临时文件；不要复制到
项目目录或用户主目录。

脚本只输出脱敏桶提示、地域、随机对象摘要标识和阶段，不输出 Secret、Token、对象内容或完整 URL。成功时退出码为 `0`，并显示
“测试对象已确认清理”。其它退出码含义：

| 退出码 | 含义 | 处理 |
|---:|---|---|
| `1` | 未预期的脚本异常 | 保存脱敏日志，交由开发排查 |
| `2` | 配置或测试桶隔离门禁失败 | 检查全部 `COS_SMOKE_*`、桶名和 `COS_BUCKET` 对比 |
| `3` | COS 请求失败或超时 | 检查地域、网络、临时凭证有效期和四项对象权限 |
| `4` | SHA256/Content-Type/删除确认或最终清理失败 | 立即按日志中的对象摘要定位执行记录；不得改用列表或递归删除，需由有权限人员对该次随机 Key 做精确复核 |

验收标准：put 成功，head/get 的 `Content-Type` 为 `application/octet-stream`，下载内容 SHA256 与随机上传内容一致，delete 后
head 返回不存在，并且最终清理再次确认不存在。真实验证完成后立即撤销短期凭证或等待其自动过期，不要把 smoke 凭证保留在生产 ERP 进程环境中。
