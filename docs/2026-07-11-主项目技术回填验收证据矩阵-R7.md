## 3. 四套 Client 的方向、变量和 Header

四套凭证不是“四个都创建在主项目入站 Client 表”。前两套是 **ERP 调主项目**，后两套是 **主项目调 ERP**；方向配置错误会造成必然的 401/503。

| 套件 | 调用方向 | 接收接口 | ERP 变量 | Header | 建议 Client ID | 配置归属 |
| --- | --- | --- | --- | --- | --- | --- |
| SSO exchange | ERP 后端 → 主项目 | `POST /api/v1/internal/sso/erp/exchange` | `ERP_SSO_CLIENT_ID/SECRET` | `X-ERP-Client-Id` / `X-ERP-Client-Secret` | `erp-sso` | 主项目保存 Secret 哈希并授予 `sso.exchange`；ERP 保存一次明文 Secret |
| business API | ERP 后端 → 主项目 | team scope、permission version、专利业务 API | `MAIN_API_CLIENT_ID/SECRET`；专利接口可选覆盖为 `IP_API_CLIENT_ID/SECRET` | `X-ERP-Service-Id` / `X-ERP-Service-Secret` | `erp-main-api` | 主项目保存 Secret 哈希并按接口授予 service 权限；ERP 保存一次明文 Secret |
| Manifest sync | 主项目权限中心 → ERP | `GET /api/v1/internal/permissions/manifest` | `ERP_MANIFEST_CLIENT_ID/SECRET` | `X-ERP-Manifest-Client-Id` / `X-ERP-Manifest-Client-Secret` | `main-permission-center` | 主项目出站环境与 ERP 入站校验环境配置同一对值；不创建为主项目入站哈希 Client |
| Employee provisioning | 主项目账号绑定 → ERP | `POST /api/v1/internal/provisioning/employees` | `ERP_PROVISION_CLIENT_ID/SECRET` | `X-Main-Provision-Client-Id` / `X-Main-Provision-Client-Secret`，另带 `Idempotency-Key` | `main-provisioning` | 主项目出站环境与 ERP 入站校验环境配置同一对值；不创建为主项目入站哈希 Client |

验收规则：

1. 四套 Client ID 必须互不相同，四套 Secret 也必须互不相同。
2. `IP_API_CLIENT_*` 留空时复用 `MAIN_API_CLIENT_*`，这仍属于同一“业务 API 套件”；如单独配置，则主项目必须把它作为额外业务服务 Client 创建并授权，且不得复用 SSO 凭证。
3. Header 名双方已经对齐。除非网关确有改写需求，不应自定义 Header；若必须改写，两侧必须成对修改并重新跑契约 smoke。
4. Manifest/provisioning 的 Secret 明文只存在双方受控出站/入站环境变量中，不应写入文档或 Git。

## 5. `kid`、公钥和私钥边界

ERP 侧需要的受控配置只有：

- `ERP_SSO_ACTIVE_KID`
- `ERP_SSO_ACTIVE_PUBLIC_KEY` 或 `ERP_SSO_ACTIVE_PUBLIC_KEY_PATH`
- 如正在轮换，再配置 `ERP_SSO_PREVIOUS_KID` 与 previous 公钥；二者必须同时存在或同时留空
- 公钥指纹、启用时间、停止接受 previous 的时间和轮换负责人

主项目私钥及其仓库外路径只属于主项目运行环境，**不得交付给 ERP**。回填“五.4”中的“仓库外私钥路径”可由主项目内部运维确认，但 ERP 联调只验收公钥、`kid` 和签名结果。首发且没有旧 key 时 previous 配置可留空；生产轮换演练前再补齐，不阻止第一次测试环境 exchange。

## 8. 联调执行顺序

1. 受控渠道交付测试地址、四套 Client、active `kid`/公钥和一个成功账号。
2. ERP 注入测试环境配置，先运行 `npm run preflight:unified-auth`，不得在输出中打印 Secret/Code/assertion。
3. 运行 `npm run smoke:main-contract`，先验证 team scope 与 permission version；准备成对的一次性 Code/state 后再验证 exchange/assertion。
4. 浏览器打通 `/sso/initiate → 主项目 continue/authorize → /sso/callback`。
5. 完成七类账号验收、Manifest 同步、Employee provisioning 和专利业务 API。
6. 同步 Manifest v1.3.0，并用获授权测试账号验收工资条导出与撤权即时失效。
7. 形成可部署提交/Tag；在预发布环境执行数据库迁移、生产 preflight、ready 探针和回滚演练。
8. 确认灰度 T0，观察固定一周；T0+7 验收通过后关闭密码登录、legacy session 和旧共享 JWT。
