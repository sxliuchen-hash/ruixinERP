# ERP 统一权限与 SSO 改造实施确认清单

## 1. 结论

ERP 侧统一权限与 SSO 改造已经完成，可以进入主项目联调阶段。

本轮已经落实以下边界：

- 主项目负责用户身份、角色、团队层级、权限分配和权限版本。
- ERP 发布自身权限目录，并在前后端执行主项目下发的权限。
- ERP 业务岗位 `boss / partner / sales / purchase / admin` 只保留为薪酬、业绩属性，不作为 SSO 权限角色。
- SSO 由 ERP 作为 RP 先生成一次性 `state` 并绑定发起浏览器，再使用主项目 60 秒一次性 Code；浏览器不接触主项目 assertion。
- ERP 使用 RS256 验证主项目 assertion，再签发自己的短会话 JWT。
- 普通 SSO 会话请求按缓存检查 `permissionVersion`；高风险请求实时检查。
- 多实例发现本地权限版本缓存落后时，会实时复核并同步清除本实例旧 team scope 缓存。
- ERP 调主项目业务 API 使用独立服务凭证，不与 SSO Code 兑换凭证混用。
- 主项目绑定 ERP 账号时，通过第四套独立凭证调用幂等 Employee 建档接口。
- 灰度期 `IP_AUTH_MODE=hybrid` 按会话来源兼容 legacy 与 `main_sso`；旧会话排空后切换 `client_credentials`。
- 登录页公开读取后端认证开关；关闭密码登录后不再展示用户名密码表单。
- 文件预览和下载不再接受 `?token=` 长效会话参数。

正式权限目录：

```text
backend/src/permissions/erp-permission-manifest.json
```

当前版本：

```text
schemaVersion: 1
application.version: 1.3.0
权限数量: 117
接口映射数量: 192
```

Manifest 中每个权限已经包含：`code`、`name`、`description`、`action`、`scopes`、`riskLevel`、`sensitive`、`routes`、`pages`、`deprecated`。内部接口会额外返回基于完整 Manifest 计算的 SHA-256 `hash`。

## 2. 主项目本轮必须提供的接口

### 2.1 主项目入口授权

主项目登录后的 ERP 按钮只能对拥有 `erp.app.view` 的用户显示。

点击按钮后，主项目只能把浏览器送到 ERP 固定 RP 发起地址：

```text
https://erp.iptt.top/sso/initiate
```

正式 R7 流程：

1. ERP 浏览器调用 `POST /api/v1/auth/sso/initiate`。
2. ERP 后端生成 32 字节随机 `state`，Redis 只保存 state 哈希及浏览器绑定哈希，并设置生产环境 `Secure + HttpOnly + SameSite=Lax` Cookie。
3. ERP 返回并跳转主项目固定地址：`/sso/continue?app=erp&state=<state>`。
4. 主项目清除地址栏查询参数后，以当前主项目登录态调用 `POST /api/v1/sso/erp/authorize`，body 必须为 `{ "state": "..." }`。
5. 主项目再次检查用户状态、ERP 绑定和 `erp.app.view`，生成随机、不可预测、60 秒有效、只能消费一次的 Code；Code 固定绑定 `audience=erp`、生产回调地址和该 state。
6. 主项目跳转固定 callback：

```text
https://erp.iptt.top/sso/callback?code=<one-time-code>&state=<state>
```

不得跳转到：

```text
https://erp.iptt.top/?token=<jwt>
```

### 2.2 Code 服务端兑换接口

ERP 当前调用：

```http
POST /api/v1/internal/sso/erp/exchange
X-ERP-Client-Id: <ERP_SSO_CLIENT_ID>
X-ERP-Client-Secret: <ERP_SSO_CLIENT_SECRET>
Content-Type: application/json
```

请求体：

```json
{
  "authorizationCode": "一次性Code",
  "state": "ERP发起并绑定浏览器的一次性state",
  "audience": "erp",
  "redirectUri": "https://erp.iptt.top/sso/callback"
}
```

主项目应先原子消费 Code，再校验 Code 记录中的 state；state 不匹配时 Code 同样已经烧毁。校验通过后返回：

```json
{
  "success": true,
  "data": {
    "assertion": "<RS256 JWT>"
  }
}
```

ERP 同时兼容主项目现行统一响应格式：

```json
{ "code": 200, "message": "兑换成功", "data": { "assertion": "<RS256 JWT>" } }
```

assertion 必须包含：

```text
alg=RS256
kid=<当前密钥编号>
iss=patent-notice-system
aud=erp
sub=<users.id>
iat
exp
jti
user.username
user.role
permissions
permissionVersion
```

其中 `permissions` 使用以下结构：

```json
{
  "erp.app.view": { "allowed": true, "scope": "all" },
  "erp.contract.view": { "allowed": true, "scope": "team" },
  "erp.expense.approve": { "allowed": true, "scope": "team" }
}
```

### 2.3 团队范围接口

ERP 当前调用：

```http
GET /api/v1/internal/users/:userId/team-scope
X-ERP-Service-Id: <MAIN_API_CLIENT_ID>
X-ERP-Service-Secret: <MAIN_API_CLIENT_SECRET>
```

期望返回：

```json
{
  "success": true,
  "data": {
    "teamUserIds": [5, 6, 9]
  }
}
```

确认规则：

- `teamUserIds` 使用主项目 `users.id`。
- 返回集合必须包含当前用户本人。
- `supervisor` 的团队范围由主项目定义；建议按 `parentId` 子树计算。
- ERP 最多缓存 5 分钟，当前默认 120 秒。
- 主项目不可用或响应格式错误时，ERP 按空集合处理，不退化为 `all`。

### 2.4 权限版本接口

ERP 当前调用：

```http
GET /api/v1/internal/users/:userId/permission-version
X-ERP-Service-Id: <MAIN_API_CLIENT_ID>
X-ERP-Service-Secret: <MAIN_API_CLIENT_SECRET>
```

期望返回：

```json
{
  "success": true,
  "data": {
    "permissionVersion": 18
  }
}
```

主项目至少应在以下事件递增版本：

- 用户被禁用。
- 用户角色或 ERP 授权变化。
- 用户密码修改或主项目执行全局会话失效。
- 团队上下级调整。
- 用户所属部门或团队范围变化。

ERP 行为：

- 普通接口：缓存校验，默认 TTL 120 秒，可配置为 1～5 分钟。
- 高风险接口：每次实时查询。
- 版本不一致：返回 401，要求用户重新从主项目进入 ERP。
- 主项目权限服务不可用：返回 503，默认拒绝高风险操作。
- legacy 旧会话在灰度期跳过该检查。

### 2.5 ERP 权限目录同步接口

主项目权限中心可拉取：

```http
GET https://erp.iptt.top/api/v1/internal/permissions/manifest
X-ERP-Manifest-Client-Id: <ERP_MANIFEST_CLIENT_ID>
X-ERP-Manifest-Client-Secret: <ERP_MANIFEST_CLIENT_SECRET>
```

响应中的 `hash` 用于判断权限目录是否变化。主项目同步时应：

- 新权限新增为待配置状态，不自动授予普通角色。
- 已发布编码不直接改名。
- `deprecated=true` 的权限至少保留一个兼容周期。
- 保存 Manifest 版本、hash、同步时间和差异审计记录。

### 2.6 Employee 幂等建档接口

主项目启用 ERP 账号绑定时调用：

```http
POST https://erp.iptt.top/api/v1/internal/provisioning/employees
X-Main-Provision-Client-Id: <ERP_PROVISION_CLIENT_ID>
X-Main-Provision-Client-Secret: <ERP_PROVISION_CLIENT_SECRET>
Idempotency-Key: <每次绑定或改岗attempt key>
Content-Type: application/json

{
  "userId": 123,
  "name": "张三",
  "employeeRole": "sales",
  "wechatUserId": "zhangsan"
}
```

返回：

```json
{
  "success": true,
  "data": {
    "employee": { "id": 18, "userId": 123 },
    "created": true
  }
}
```

实现规则：

- 以 `employees.user_id` 幂等创建或查找，重复请求不会产生第二条员工档案。
- 已存在时只同步姓名、ERP 岗位和非空企微标识。
- 不覆盖工资、职级、入职日期、社保、分成等 ERP 人工维护字段。
- 建档凭证与 SSO、业务 API、Manifest 凭证完全独立。
- 缺少凭证时 503，错误凭证 401，缺少合法 `Idempotency-Key` 时 400。

## 3. SSO 回调和 ERP 登录态

| 环境 | 固定回调地址 |
| --- | --- |
| 本地/测试默认值 | `http://localhost:5173/sso/callback` |
| 生产 | `https://erp.iptt.top/sso/callback` |

ERP 浏览器先创建 RP state：

```http
POST /api/v1/auth/sso/initiate
Content-Type: application/json

{ "redirect": "/contracts" }
```

响应设置浏览器绑定 HttpOnly Cookie，并返回 `state`、严格固定的主项目 `redirectUrl` 和有效期。生产 state 默认 120 秒，允许配置范围为 60～300 秒。

callback 浏览器读取 `code/state` 后立即把地址栏和当前 history 条目清理为 `/sso/callback`，再提交：

```http
POST /api/v1/auth/sso/exchange
Content-Type: application/json

{
  "code": "一次性Code",
  "state": "与当前浏览器HttpOnly Cookie绑定的state"
}
```

ERP 后端使用 Redis Lua 原子读取并删除 state。缺 Cookie/state、跨浏览器、重复 callback、并发重复消费、过期 state 或 Redis 不可用均 fail-closed，且不会向主项目发送 exchange。合法请求会把同一 state 放入主项目 exchange body。

ERP 后端验签后返回 ERP 自己的短会话：

```json
{
  "success": true,
  "data": {
    "token": "<ERP session JWT>",
    "user": {},
    "permissions": {},
    "permissionVersion": 18,
    "authSource": "main_sso"
  }
}
```

当前 ERP 会话实现为 HS256 JWT，生产环境强制使用独立 `ERP_SESSION_SECRET`，默认有效期 2 小时。主项目 assertion 不会返回给浏览器，也不会被 ERP 当作长期会话保存。

## 4. 公钥和 `kid` 轮换

ERP 支持 active/previous 两把公钥并存：

```text
ERP_SSO_ACTIVE_KID
ERP_SSO_ACTIVE_PUBLIC_KEY 或 ERP_SSO_ACTIVE_PUBLIC_KEY_PATH
ERP_SSO_PREVIOUS_KID
ERP_SSO_PREVIOUS_PUBLIC_KEY 或 ERP_SSO_PREVIOUS_PUBLIC_KEY_PATH
```

轮换顺序：

1. 主项目生成新密钥对，但暂不签发。
2. ERP 把新公钥配置为 active，旧公钥移到 previous。
3. 主项目开始用新私钥和新 `kid` 签发 assertion。
4. 等待旧 assertion 最大有效期结束。
5. ERP 删除 previous 公钥。

未知 `kid`、缺失 `kid`、非 RS256 算法默认拒绝。`ERP_SSO_ALLOW_LEGACY_NO_KID=true` 只允许旧联调环境临时开启。

## 5. 数据范围正式规则

### 5.1 已实现 `self/team/all` 的模块

| 模块 | 权限范围 | ERP 属主字段 | self | team | all |
| --- | --- | --- | --- | --- | --- |
| 合同 | `self/team/all` | `owner_id` | `owner_id=当前 users.id` | `owner_id IN teamUserIds` | 不加属主过滤 |
| 收付款 | `self/team/all` | `created_by` | 当前用户创建 | 团队用户创建 | 全部 |
| 报销 | `self/team/all` | `created_by` | 当前用户创建 | 团队用户创建 | 全部 |
| 借款 | `self/team/all` | `created_by` | 当前用户创建 | 团队用户创建 | 全部 |
| 专利库存 | `self/team/all` | `created_by` | 当前用户创建 | 团队用户创建 | 全部 |
| 交易项目 | `self/team/all` | `created_by OR owner_id` | 任一字段为当前用户 | 任一字段属于团队用户 | 全部 |
| 通知中心 | `self/all` | `user_id` | 当前用户私信 | 不支持 | 当前用户私信和 `user_id=NULL` 只读系统广播；广播不计个人未读数且不能被个人修改/删除 |

行级过滤已覆盖列表、详情、修改、删除、确认、还款、出售/撤销出售、统计汇总和相关 raw SQL。缺失或非法 scope 默认使用不可匹配条件，不会退化为全部数据。

创建行为说明：合同、收付款、报销、借款、库存和项目的新记录默认绑定当前 `users.id`；`team/all` 不表示可以伪造创建人。

### 5.2 当前只支持 `all` 的模块

以下模块尚无稳定属主字段，或按业务定义属于公司级数据，因此 Manifest 只声明 `all`：

- ERP 入口、首页看板。
- 银行账户、成本、对账、系统设置、分类规则。
- 客户、供应商、发票。
- 历史导入、审计日志，以及只支持公司级范围的发票/成本导出。
- 企业微信、员工档案。
- 业绩、采购提成、业绩导入、薪资规则、工资条。
- 年费查询、文件下载。
- 专利异常告警、库存批量导入、库存批量删除。

后续只有在 service 查询层完成真实行级过滤并补齐测试后，才能把这些权限扩展为 `self/team`。

## 6. 用户与员工档案映射

ERP 已按以下原则实现：

- SSO 永久用户标识使用主项目 `users.id`。
- SSO 用户不再依赖 ERP 直接查询主项目用户表来建立登录态。
- `employees.user_id` 已增加命名唯一约束和幂等迁移脚本：一个主项目账号最多绑定一个 ERP 员工档案；上线前运行 `npm run migrate:employee-user-id-unique`。
- `/api/v1/internal/provisioning/employees` 已支持主项目绑定时自动建档和改岗同步。
- `employees.role` 仅用于薪酬、业绩和岗位业务规则，不参与 ERP 权限判断。

仍需主项目和业务负责人确认：

- 企业微信员工优先使用 `users.id` 还是 `wechat_userid` 作为同步关联键；建议主键使用 `users.id`，`wechat_userid` 作为外部标识。
- 企业微信发现新员工时，是仅创建 ERP Employee，还是发起主项目账号创建申请。
- 新账号角色、上级和 ERP 权限由谁审批。
- 离职流程是否同步禁用主项目账号并递增 `permissionVersion`。

## 7. ERP 调主项目业务 API

SSO 认证与业务 API 认证已经分开。

目标配置：

```text
IP_AUTH_MODE=client_credentials
MAIN_API_CLIENT_ID=<ERP业务服务账号>
MAIN_API_CLIENT_SECRET=<ERP业务服务密钥>
```

也可为专利接口单独配置：

```text
IP_API_CLIENT_ID
IP_API_CLIENT_SECRET
```

用户请求携带：

```http
X-ERP-Service-Id: <service id>
X-ERP-Service-Secret: <service secret>
X-Acting-User-Id: <users.id>
X-Acting-Permission-Version: <version>
```

后台扫描任务携带：

```http
X-ERP-Service-Id: <service id>
X-ERP-Service-Secret: <service secret>
X-ERP-Job-Name: patent-anomaly-scan
```

浏览器 ERP Token 不会在 `client_credentials` 模式下透传主项目。

SSO 灰度期如需同时承接旧密码会话和新 SSO 会话，使用：

```text
IP_AUTH_MODE=hybrid
```

- `authSource=main_sso`：服务凭证 + acting user + `permissionVersion`。
- `authSource=legacy`：仅灰度期继续透传旧 Bearer JWT。
- 后台任务：始终使用服务凭证 + `X-ERP-Job-Name`。
- 未知会话来源：fail-closed。

当前业务接口清单：

| 方法 | 主项目接口 | 调用场景 | 主项目建议服务权限 |
| --- | --- | --- | --- |
| POST | `/api/v1/patent-query/detail` | 用户年费代查、库存同步、后台扫描 | `ip.patent_query.execute` |
| GET | `/api/v1/patent-fee/detail/:no` | 年费详情降级查询 | `ip.patent_fee.read` |
| GET | `/api/v1/patent-fee/list` | 年费列表 | `ip.patent_fee.read` |
| GET | `/api/v1/patent-fee/dashboard` | 年费看板 | `ip.patent_fee.read` |
| GET | `/api/v1/patents/no/:no` | 专利基本信息、后台扫描 | `ip.patent.read` |

主项目需要区分：

- 有 `X-Acting-User-Id`：代表当前登录用户，继续执行该用户在主项目的数据权限。
- 有 `X-ERP-Job-Name` 且无 acting user：代表 ERP 后台任务，仅按服务账号权限执行。

建议主项目为这些调用增加服务级配额、限流、请求审计和代查幂等键。

应急回滚模式：

```text
IP_AUTH_MODE=legacy_shared_jwt
```

该模式仅用于主项目尚未完成服务凭证接口时临时回滚；完成联调后应关闭并停止共享 `JWT_SECRET`。

### 12.1 主项目测试环境契约烟雾检查

主项目回填测试地址、业务服务凭证和测试用户后，可在 `backend` 目录直接运行：

`MAIN_SSO_BASE_URL` 是该命令的必填项；未显式设置时命令会直接失败，不会使用 ERP 运行时的 `127.0.0.1` 默认值。

```powershell
$env:MAIN_SSO_BASE_URL='https://<主项目测试地址>'
$env:MAIN_API_CLIENT_ID='<ERP业务服务账号>'
$env:MAIN_API_CLIENT_SECRET='<ERP业务服务密钥>'
$env:MAIN_CONTRACT_SMOKE_USER_ID='<主项目测试用户users.id>'
npm run smoke:main-contract
```

默认只发送两个只读 GET 请求：

- `team-scope`：要求 `teamUserIds` 为不重复的正整数数组，并包含测试用户本人。
- `permission-version`：要求 `permissionVersion` 为非负整数。

如需同时验证一次性 Code 兑换，补充 SSO Client、公钥、callback 配置，并仅在本次命令前临时设置：

```powershell
$env:SSO_AUTHORIZATION_CODE='<刚生成且尚未使用的一次性Code>'
$env:SSO_STATE='<该Code绑定的RP state>'
npm run smoke:main-contract
Remove-Item Env:SSO_AUTHORIZATION_CODE
Remove-Item Env:SSO_STATE
```

`SSO_AUTHORIZATION_CODE` 和 `SSO_STATE` 必须成对设置；设置后会消费一次性 Code。命令会验证主项目返回的 RS256 assertion，并要求 assertion 中的 `permissionVersion` 与本轮 `permission-version` GET 结果完全一致；它不生成或输出 ERP Token，输出也不会包含 Secret、完整 Code、state 或 assertion。命令仅通过 HTTP 调用主项目测试接口，不加载 ERP 数据库配置、不执行数据库连接、不修改主项目业务数据。
