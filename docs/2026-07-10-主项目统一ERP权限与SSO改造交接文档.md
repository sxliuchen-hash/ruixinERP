# 主项目统一 ERP 权限与 SSO 改造交接文档

> 2026-07-11 实施状态：ERP 侧代码改造与本地自动化验收已完成，尚未完成真实环境联调或生产上线签字。正式权限目录为
> `backend/src/permissions/erp-permission-manifest.json`（v1.3.0，117 个权限，
> 192 条接口映射）。主项目 R7 代码基线 `c633dc0` 已具备权限中心、一次性 Code/state、
> 团队范围和权限版本接口；当前剩余工作是受控环境地址、四套凭证、公钥/`kid`、测试账号、真实联调、生产基础设施门禁和灰度下线旧认证。ERP 侧最终实现与联调参数见
> `docs/2026-07-10-ERP统一权限与SSO改造实施确认清单.md`。
>
> 本文统一采用 R7 协议：ERP 作为 RP 先生成并绑定 `state`，主项目再签发与该
> `state` 绑定的一次性 Code。旧的“主项目直接生成 Code 跳 callback”流程已经废弃。

## 1. 文档目的

本文用于将“主项目统一认证、统一配置 ERP 权限，ERP 负责执行本系统业务权限和数据范围”的改造方案交接给主项目开发人员。

本轮目标不是简单增加一个跳转按钮，而是建立可持续扩展的跨系统权限协作机制：

1. 用户只需登录主项目，即可按权限进入 ERP。
2. 主项目作为用户、角色、组织层级和授权策略的唯一真源。
3. ERP 负责声明自身有哪些权限项，不要求主项目猜测 ERP 功能。
4. 主项目负责配置各角色拥有哪些 ERP 权限及数据范围。
5. ERP 后端必须执行主项目下发的权限，不能只依赖前端隐藏按钮。
6. 停止使用 URL 携带长效 JWT 的跨系统跳转方式。

## 3. 总体职责边界

| 能力 | 负责项目 | 说明 |
| --- | --- | --- |
| 用户登录 | 主项目 | ERP 不再独立验证主项目用户密码 |
| 用户角色 | 主项目 | ERP 不维护第二套角色真源 |
| 团队和上下级 | 主项目 | supervisor/team 范围由主项目定义 |
| ERP 权限目录 | ERP | ERP 最清楚自身模块、接口和操作 |
| 角色权限分配 | 主项目 | 管理员在主项目权限中心配置 |
| SSO 授权 | 主项目 | 主项目检查权限后发放一次性授权码 |
| ERP 接口权限校验 | ERP | ERP 根据权限编码执行后端校验 |
| ERP 行级数据过滤 | ERP | ERP 数据位于 ERP 数据库，必须在 ERP service 层过滤 |
| 权限变更失效 | 主项目发起，ERP配合 | 通过 permissionVersion/tokenVersion 使旧会话失效 |

核心原则：

> ERP 发布权限目录，主项目管理授权策略，ERP 执行授权结果。

## 4. 正式 R7 SSO 流程

```text
用户已登录主项目
  → 主项目前端点击“进入 ERP”
  → 浏览器进入固定地址 https://erp.iptt.top/sso/initiate
  → ERP 后端生成一次性 state，并通过 HttpOnly Cookie 绑定当前浏览器
  → 浏览器跳转主项目 /sso/continue?app=erp&state=xxx
  → 主项目前端读取并立即清除地址栏 state
  → POST /api/v1/sso/erp/authorize，body={ state }
  → 主项目检查用户状态、ERP 绑定和 erp.app.view
  → 主项目生成 60 秒、单次使用、绑定 state 的随机 Code
  → 浏览器跳转 https://erp.iptt.top/sso/callback?code=xxx&state=xxx
  → ERP 前端读取后立即清除地址栏 Code/state
  → ERP 前端把 Code/state 提交给 ERP 后端，并携带浏览器绑定 Cookie
  → ERP 后端消费 RP state，再调用主项目内部兑换接口
  → 主项目原子消费 Code，校验 state/audience/redirectUri，并重新检查用户状态和权限
  → 主项目返回 ERP 专用身份断言和有效权限
  → ERP 建立本系统登录态
```

其中 `state` 必须由 ERP 生成，主项目不得自行替换；Code 与 state 必须成对绑定。
跨浏览器、缺少 Cookie、state 不匹配、重复回调或 Redis 不可用时均应默认拒绝。

禁止直接跳转：

```text
https://erp.iptt.top?token=<主项目长效JWT>
```

## 5. ERP 权限目录 Manifest

### 5.1 权限目录归属

ERP 项目必须维护版本化权限目录，建议文件：

```text
backend/src/permissions/erp-permission-manifest.json
```

主项目不应长期手工维护 ERP 权限名称。主项目只同步 Manifest 并配置角色授权。

### 5.2 权限编码规范

统一格式：

```text
erp.<module>.<action>
```

示例：

```text
erp.app.view
erp.contract.view
erp.contract.create
erp.contract.update
erp.contract.delete
erp.contract.confirm
erp.expense.view
erp.expense.approve
erp.payroll.view
erp.payroll.export
erp.system.update
```

权限编码一经上线不得直接改名。需要改名时新增编码，旧编码进入 deprecated 状态并保留一个兼容周期。

### 5.3 数据范围

功能权限和数据范围必须分开：

```text
none  无权限
self  仅本人数据
team  本人及团队范围
all   全部数据
```

例如：

```json
{
  "permission": "erp.expense.view",
  "allowed": true,
  "scope": "team"
}
```

不要把数据范围编码为多个权限，例如不要创建：

```text
erp.expense.view_self
erp.expense.view_team
erp.expense.view_all
```

### 5.4 Manifest 示例

```json
{
  "application": {
    "code": "erp",

    "version": "1.0.0"

        {
          "code": "erp.contract.view",

    },
    {
      "code": "payroll",
```


### 7.4 新增 SSO 授权接口

主项目需要提供：

```text
POST /api/v1/sso/erp/authorize
```

该接口由主项目 `/sso/continue` 页面使用当前登录态调用，请求体必须携带 ERP 生成的
`state`：

```json
{
  "state": "ERP生成的一次性state"
}
```

成功响应：

```json
{
  "code": 200,
  "message": "授权成功",
  "data": {
    "redirectUrl": "https://erp.iptt.top/sso/callback?code=一次性随机码&state=ERP生成的一次性state",
    "expiresIn": 60
  }
}
```

服务端流程：

1. 验证登录态；
2. 检查用户状态；
3. 检查用户已完成 ERP 绑定或满足主项目定义的 ERP 准入条件；
4. 检查 `erp.app.view`；
5. 校验 `state` 符合 `^[A-Za-z0-9_-]{32,200}$`；
6. 生成至少 32 字节随机 Code；
7. Redis 只存授权码哈希；
8. TTL 60 秒；
9. 绑定 `state`、`audience=erp`、用户 ID 和固定生产回调地址；
10. `redirectUrl` 只能由服务端根据白名单生成，不能接受前端传入任意地址；
11. 记录审计日志，但不得记录完整 Code 或 state。

主项目还需要提供固定公开页面：

```text
GET /sso/continue?app=erp&state=<state>
```

该页面读取参数后必须立即清理浏览器 URL/history，再调用 authorize；任何错误都不得
回退到 URL Token 或无 state 的旧流程。

### 7.5 新增 ERP 服务端兑换接口

建议新增：

```text
POST /api/v1/internal/sso/erp/exchange
```

该接口只能由 ERP 后端调用，使用独立服务凭证：

```text
ERP_SSO_CLIENT_ID
ERP_SSO_CLIENT_SECRET
```

请求示例：

```json
{
  "authorizationCode": "一次性随机码",
  "state": "ERP生成并绑定浏览器的一次性state",
  "audience": "erp",
  "redirectUri": "https://erp.iptt.top/sso/callback"
}
```

兑换时必须：

1. 原子消费授权码，推荐 Redis `GETDEL`；
2. 即使后续 state 校验失败，已消费的 Code 也不得恢复；
3. 检查未过期、未使用、state、audience 和 redirectUri 完全一致；
4. 重新查询用户状态、ERP 绑定和角色；
5. 再次计算 ERP 有效权限和 scope；
6. 返回 ERP 专用身份断言；
7. 兑换失败统一 fail-closed。

返回示例：

```json
{
  "code": 200,
  "message": "兑换成功",
  "data": {
    "assertion": "主项目签发的ERP专用短期令牌",
    "user": {
      "id": 123,
      "username": "zhangsan",
      "realName": "张三",
      "role": "supervisor"
    },
    "permissions": {
      "erp.app.view": { "allowed": true, "scope": "all" },
      "erp.contract.view": { "allowed": true, "scope": "team" },
      "erp.expense.approve": { "allowed": true, "scope": "team" },
      "erp.payroll.view": { "allowed": false, "scope": "none" }
    },
    "permissionVersion": 18
  }
}
```

### 7.6 ERP 专用签名

推荐使用非对称签名：

```text
主项目：ERP_SSO_PRIVATE_KEY
ERP：ERP_SSO_PUBLIC_KEY
```

ERP 只能验签，不能伪造主项目身份。

身份断言至少包含：

```text
iss
aud=erp
sub=userId
username
role
permissions 或 permissionSnapshotId
permissionVersion
jti
iat
exp
```

第一版有效期建议不超过 2 小时；过期后重新从主项目进入 ERP。

### 7.7 主项目前端入口

主项目增加“进入 ERP”按钮。

按钮显示必须依据后端计算的 `erp.app.view`，不得在前端硬编码角色数组。

点击后：

1. 跳转固定 ERP 地址 `https://erp.iptt.top/sso/initiate`；
2. 不在主项目入口按钮中自行生成 Code 或 state；
3. 不允许前端自行传入任意 callback/redirect URL；
4. 不携带主项目长效 JWT；
5. 用户无 `erp.app.view` 时按钮不可见，直接访问 authorize 仍必须返回 403。

### 7.8 ERP Employee 建档

主项目当前 ERP 绑定策略要求 `provisioningRequired=true`。绑定或改岗时调用：

```http
POST https://erp.iptt.top/api/v1/internal/provisioning/employees
X-Main-Provision-Client-Id: <ERP_PROVISION_CLIENT_ID>
X-Main-Provision-Client-Secret: <ERP_PROVISION_CLIENT_SECRET>
Idempotency-Key: <binding attempt key>
```

请求字段为 `userId/name/employeeRole/wechatUserId`。ERP 按 `employees.user_id`
幂等创建或同步，只更新姓名、岗位和非空企微标识，不覆盖工资、职级、入职日期等
人工维护字段。建档凭证必须与 SSO、业务 API、Manifest 三个通道完全分离。

15. 登录页已按后端认证开关 fail-closed 隐藏密码表单；
16. 已提供认证预检、主项目契约烟雾检查和部署 Nginx 静态门禁。

ERP 当前剩余工作仅为真实环境配置和联调：接收主项目接口地址、四套独立凭证、RS256 公钥与 `kid`、测试账号及角色授权结果，执行预检和 smoke，通过后再关闭旧密码登录。

主项目接口字段、权限编码、scope 和失效语义必须与本文及
`docs/2026-07-10-ERP统一权限与SSO改造实施确认清单.md` 保持一致。

## 9. 权限变更与会话失效

主项目建议维护 `permissionVersion`。

以下操作必须递增版本：

- 修改角色权限；
- 修改用户角色；
- 禁用或删除用户；
- 调整用户团队层级；
- 修改用户特殊权限（如后续支持）。

ERP assertion 携带签发时的版本。ERP 可采用：

- 普通查询：缓存校验 1～5 分钟；
- 高风险操作：实时向主项目校验 permissionVersion；
- 发现版本不一致：清除 ERP 登录态并要求重新从主项目进入。

建议实时校验的高风险操作：

```text
工资生成、确认、支付、导出
财务确认和审批
银行账户转账
批量导入
批量删除
系统配置修改
高敏感数据导出
```

## 10. Manifest 同步规则

1. 新权限：同步后默认拒绝。
2. 权限名称修改：可直接更新显示名称，不改变编码。
3. 权限编码废弃：先标记 deprecated，不立即物理删除。
4. 权限移除：主项目显示受影响角色和用户后再确认。
5. Manifest 必须包含 version 和 hash。
6. 同步操作必须记录操作日志。
7. ERP Manifest 与路由权限不一致时，ERP CI 必须失败。

## 11. ERP 后续 CI 权限门禁

ERP 应增加自动测试：

1. 扫描后端所有 `requirePermission('...')`；
2. 验证权限编码存在于 Manifest；
3. 扫描前端所有 `can('...')`；
4. 验证前后端权限编码一致；
5. 检查敏感写接口是否配置权限中间件；
6. 检查 Manifest 中长期未使用的权限；
7. 检查新增路由是否明确声明公开或受保护；
8. 禁止新增角色硬编码白名单。

## 12. 推荐初始角色配置

以下为初始建议，最终由业务负责人确认：

| 角色 | ERP入口 | 默认范围 | 说明 |
| --- | --- | --- | --- |
| admin | 允许 | all | 全部 ERP 权限 |
| process | 允许 | all | 财务、合同、库存等业务能力；工资权限单独确认 |
| supervisor | 允许 | team | 查看和管理团队范围数据 |
| agent | 允许 | self | 仅本人合同、报销、业绩等数据 |
| client | 禁止 | none | 不进入内部 ERP |
| sub_account | 禁止 | none | 不进入内部 ERP |
| sub_department | 禁止 | none | 不进入内部 ERP |

工资、账户转账、系统配置、删除、批量导入导出等权限不得仅根据角色默认放行，必须在主项目权限中心明确配置。

## 13. 安全要求

1. 禁止 URL 携带长效 JWT。
2. `state` 必须由 ERP 生成，使用 Redis 哈希存储并通过 HttpOnly Cookie 绑定浏览器。
3. initiate 与 callback 两端的 `state` 均须匹配 `^[A-Za-z0-9_-]{32,200}$`。
4. SSO Code 最长 60 秒有效且只能使用一次。
5. Redis 只存 Code/state 哈希，不存明文 Code/state。
6. Code 必须绑定 state、audience 和固定回调地址。
7. Code/state 从页面读取后必须立即从 URL/history 清除，且不得进入 Web Storage。
8. 内部兑换接口必须验证 ERP 服务身份。
9. assertion 必须校验算法、`kid`、issuer、audience、expiresAt 和 jti。
10. 新权限默认拒绝。
11. 主项目权限查询失败时 fail-closed。
12. ERP 高风险操作不能仅信任前端权限。
13. 日志不得记录完整 Code、state、Token、assertion、私钥或服务密钥。
14. 权限同步、角色授权和 SSO 登录必须进入操作日志。
15. 正式上线前必须完成越权、重放、跨浏览器和权限实时失效测试。

## 14. 推荐实施顺序

### 阶段一：主项目权限注册中心

- 新增 applications、permission_definitions、role_permission_grants；
- 支持导入 ERP Manifest；
- 增加 ERP 权限矩阵管理页面；
- 扩展 PermissionService 的应用权限计算能力。

### 阶段二：主项目 SSO

- 增加固定 `/sso/continue` 页面；
- 增加 state 入参的 authorize 和内部 exchange 接口；
- 增加与 ERP state 绑定的一次性 Code；
- 增加 ERP assertion 签发；
- 增加 permissionVersion；
- 暂不显示 ERP 入口按钮。

### 阶段三：ERP 接入

- ERP 增加 Manifest；
- 增加 `/sso/initiate`、RP state、浏览器绑定 Cookie、SSO callback 和 exchange；
- 支持 assertion 验签；
- 支持 permission/scope 中间件。

### 阶段四：入口开放

- 主项目显示“进入 ERP”；
- 按角色进行联调；
- 验证权限变更和用户禁用；
- 保留 ERP 旧登录作为临时应急入口。

### 阶段五：旧认证下线

- 关闭 ERP 用户名密码登录；
- 移除 MainUser.password 查询；
- 移除共享 JWT Secret 依赖；
- 移除 URL Token 接收；
- 删除 ERP 静态角色白名单。

## 15. 上线和回滚开关

建议增加配置：

```text
主项目：ERP_SSO_ENABLED=false
主项目：ERP_PERMISSION_CENTER_ENABLED=false
ERP：ENABLE_SSO_LOGIN=false
ERP：ENABLE_PASSWORD_LOGIN=true
```

上线时依次开启；出现故障时可关闭 SSO，临时恢复 ERP 旧密码登录，不回滚数据库权限目录。

## 16. 验收标准

### 主项目验收

- admin 能看到并进入 ERP；
- 未授权角色看不到入口；
- 未授权用户直接调用 authorize 返回 403；
- Code 超时后不能兑换；
- Code 第二次兑换失败；
- redirect URL 无法被篡改；
- 新权限同步后默认未授权；
- 修改角色权限后 permissionVersion 递增；
- 所有操作有审计日志。

### 联调验收

- admin 获得 all 范围；
- process 获得配置的全局能力；
- supervisor 获得 team 范围；
- agent 获得 self 范围；
- client 类角色无法进入 ERP；
- ERP 前端隐藏无权菜单；
- 直接调用无权 ERP 接口仍返回 403；
- 团队用户不能读取其他主管团队数据；
- agent 不能通过修改参数读取其他用户数据；
- 用户禁用或权限修改后旧 ERP 会话按设计失效。
- state 缺失、格式错误、跨浏览器不匹配、重复兑换和过期均被拒绝；
- Code 与 state 不匹配时 Code 已烧毁，不能再次使用；
- initiate 只能跳转主项目固定 `/sso/continue?app=erp&state=...`；
- callback 读取 Code/state 后立即清理地址栏，并且 Web Storage 中不存在 Code/state；
- 主项目或 Redis 不可用时不降级为无 state、共享 JWT 或 URL Token 登录。
