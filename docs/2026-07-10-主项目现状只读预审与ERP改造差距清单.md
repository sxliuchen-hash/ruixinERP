## 2. 历史 `main` 基线总体结论

主项目当前不能直接与 ERP 开展真实 SSO 和统一权限联调。

当前存在 7 个阻塞项：

1. 没有 ERP 入口、一次性 Code authorize 和服务端 exchange。
2. 当前只签发普通 HS256 JWT，没有 ERP 要求的 RS256 assertion 和 `kid`。
3. 当前权限体系不能表达 ERP 的 117 个权限和逐权限 `self/team/all`。
4. 没有 ERP team scope 内部接口。
5. 没有符合 ERP 契约的 `permissionVersion` 接口和完整失效事件。
6. 专利业务接口不支持独立服务凭证、acting user 和后台 job 身份。
7. 没有 ERP Manifest 拉取、存储、差异同步和角色授权能力。

可以复用的基础：

- `users.id`、用户状态、角色、部门和 `parentId` 组织树。
- 已有递归下级查询和循环保护。
- 已有 Redis `tokenVersion` 会话失效机制。
- 已有静态 `PermissionService` 权限内核和权限缓存。
- ERP 当前需要调用的 5 条专利业务接口已经存在。
- 主项目生产域名和后端端口已经明确。

## 4. 阻塞项一：SSO Code 和 ERP 入口

### 当前状态

主项目路由只注册普通密码登录、登出和个人信息：

```text
backend/src/routes/auth.js:8-55
backend/src/app.js:259-287
```

当前不存在：

```text
POST /api/v1/sso/erp/authorize
POST /api/v1/internal/sso/erp/exchange
```

主项目前端顶部和菜单中也没有“进入 ERP”入口：

```text
frontend/src/layout/MainLayout.vue:91-121
frontend/src/layout/MainLayout.vue:371
```

### 主项目需要新增

1. 登录用户调用的 authorize 接口。
2. 60 秒一次性 Code，绑定 `userId/audience/redirectUri/expiresAt`。
3. Redis 只保存 Code 哈希，使用 `GETDEL` 或等价事务单次消费。
4. ERP 后端调用的 exchange 内部接口。
5. 主项目前端 ERP 入口按钮。
6. 按钮只依据 `erp.app.view`，不能依据角色或旧 `erp` tag。
7. authorize 返回 302，或返回服务端生成的 `redirectUrl` 供前端跳转。
8. 跳转固定为：

```text
https://erp.iptt.top/sso/callback?code=<one-time-code>&state=<erp-generated-state>
```

不得把主项目 JWT 放入 URL。

## 5. 阻塞项二：RS256 assertion

### 当前状态

主项目普通 JWT 载荷只有：

```text
id
username
role
tv
```

当前没有：

```text
RS256
kid
issuer/audience
sub/jti
permissions
permissionVersion
active/previous 密钥轮换
```

ERP 会拒绝当前普通 JWT，不能把它直接作为 assertion。

### 主项目需要新增

- ERP 专用 RSA 密钥对，私钥只保存在主项目。
- active/previous `kid` 配置和轮换流程。
- ERP assertion 专用签发服务。
- 正式 claim：

```text
iss=patent-notice-system
aud=erp
sub=<users.id 十进制字符串>
iat/exp/jti
user.id/user.username/user.role
permissions
permissionVersion
```

`user.id` 必须与 `sub` 数值相同。

## 6. 阻塞项三：ERP 权限目录和授权模型

### 当前状态

主项目当前主要有两套权限表达：

1. 后端静态 `角色 × 资源类型 × 操作`。
2. 前端栏目按角色和 tags 配置。

现有栏目配置页面没有 ERP 的 117 个权限，也不能配置每个权限的 `self/team/all`：

```text
frontend/src/views/system/MenuPermissionConfig.vue:21-64
```

旧 `erp` tag 只代表可调用专利代查接口，不等于 `erp.app.view`，也不能代替正式 ERP 授权。

### 主项目需要新增

建议建立独立的跨应用权限注册中心，至少能保存：

```text
applications
application_permissions
role_application_permission_grants
permission_manifest_versions
```

每条角色授权至少包含：

```text
applicationCode=erp
permissionCode=erp.<module>.<action>
allowed=true|false
scope=self|team|all
```

同步规则：

- 从 ERP Manifest 内部接口拉取权限目录。
- 保存 `application.version/hash/lastSyncTime`。
- 新权限默认拒绝。
- 只允许选择 Manifest 声明的 scopes。
- deprecated 权限保留兼容周期。
- 授权变更递增相关用户 `permissionVersion`。

主项目已有的专利、官文等静态权限可以暂时保留；ERP 跨应用权限作为独立扩展，不要求一次性重写主项目全部权限内核。

## 7. 阻塞项四：team scope

### 当前状态

主项目已有可复用算法：

```text
userService.getAllDescendants(userId)
```

该实现：

- 按 `parentId` 递归全部子树。
- 排除 `status != 1` 的用户。
- 使用 visited 防止循环。

但是当前没有 ERP 要求的内部接口和服务凭证认证。

### 主项目需要新增

```http
GET /api/v1/internal/users/:userId/team-scope
X-ERP-Service-Id: <MAIN_API_CLIENT_ID>
X-ERP-Service-Secret: <MAIN_API_CLIENT_SECRET>
```

响应：

```json
{
  "success": true,
  "data": {
    "teamUserIds": [5, 6, 9]
  }
}
```

建议复用 `getAllDescendants()`，返回“本人 + 所有启用后代”的 `users.id`。

主项目现有 `PermissionCache` 的子树默认缓存为 3600 秒：

```text
backend/src/permissions/PermissionCache.js:65
```

ERP 自身最多缓存 300 秒，因此新的内部 team scope 接口不应直接暴露一小时旧数据；建议使用更短缓存或在团队调整时可靠清理。

## 8. 阻塞项五：permissionVersion

### 当前状态

现有 `tokenVersion` 已覆盖：

- 登出。
- 修改和重置密码。
- 用户禁用。
- 用户角色变化。

当前未覆盖：

- ERP 权限或 scope 变化。
- 用户 tags 变化。
- 团队上下级变化对相关主管的影响。
- Manifest 授权变化。

团队调整目前只清权限缓存，没有递增用户版本：

```text
backend/src/services/userService.js:441-484
```

现有 `tokenVersion` 在 Redis 和本地缓存都不可用时可能返回 `null` 并跳过验证，不适合作为内部权限版本接口的 fail-closed 响应源。

### 主项目需要决定

可选方案 A：扩展现有 `tokenVersion`。

- 所有 ERP 授权和团队变化都同步 bump。
- 新增稳定、可查询的内部接口。
- 内部接口失败时明确返回服务错误，不能返回不确定版本。

可选方案 B：新增持久化 `permission_version`。

- 在 users 表增加非负整数列，或建立独立用户权限版本表。
- ERP 授权和团队变化事务内递增。
- 登录会话 `tokenVersion` 和 ERP `permissionVersion` 可以分别维护。

无论选择哪种方案，都必须提供：

```http
GET /api/v1/internal/users/:userId/permission-version
X-ERP-Service-Id: <MAIN_API_CLIENT_ID>
X-ERP-Service-Secret: <MAIN_API_CLIENT_SECRET>
```

## 9. 阻塞项六：业务 API 服务凭证

### 当前状态

ERP 需要的业务路径已经存在：

```text
POST /api/v1/patent-query/detail
GET  /api/v1/patent-fee/detail/:patentNo
GET  /api/v1/patent-fee/list
GET  /api/v1/patent-fee/dashboard
GET  /api/v1/patents/no/:patentNo
```

成功响应格式也与 ERP 兼容。

阻塞点在认证：

- `/patent-query` 强制普通 Bearer JWT + admin/`erp|finance` tag。
- 年费和专利接口强制普通 Bearer JWT + 角色权限。
- 没有服务 Client Credentials。
- 没有 acting user。
- 没有后台 job 身份。

### 主项目需要新增

独立服务认证中间件，支持：

```http
X-ERP-Service-Id
X-ERP-Service-Secret
```

用户代表请求：

```http
X-Acting-User-Id
X-Acting-Permission-Version
```

后台任务：

```http
X-ERP-Job-Name: patent-anomaly-scan
```

执行规则：

- acting user：同时检查服务权限和当前用户数据权限。
- 后台 job：只按服务账号最小权限执行，不伪造 admin 用户。
- 记录 `serviceId/actingUserId/jobName/path/result` 审计。
- SSO 兑换凭证与业务 API 凭证必须分离。

## 10. 阻塞项七：Manifest 同步

### 当前状态

主项目没有：

- ERP Manifest 拉取客户端。
- Manifest 入站凭证配置。
- version/hash 存储。
- 权限差异同步任务。
- 新权限默认拒绝逻辑。
- ERP 角色权限管理 UI。

### 主项目需要新增

主项目调用：

```http
GET https://erp.iptt.top/api/v1/internal/permissions/manifest
X-ERP-Manifest-Client-Id: <ERP_MANIFEST_CLIENT_ID>
X-ERP-Manifest-Client-Secret: <ERP_MANIFEST_CLIENT_SECRET>
```

当前 Manifest：

```text
schemaVersion=1
application.version=1.3.0
30 modules
117 permissions
192 routes
```

建议提供“自动同步 + 管理员手动同步”两种入口。

## 11. 主项目前端改造差距

当前前端没有 ERP 入口和应用权限 Store。

需要新增：

1. `erpSso.js`，调用主项目 authorize 接口。
2. 当前用户权限状态：`permissions/permissionVersion/can()`。
3. 顶部“进入 ERP”按钮。
4. 只按 `erp.app.view` 控制按钮。
5. 使用后端返回的 `redirectUrl`，不自行拼接 Token。
6. loading、403、配置错误和网络失败提示。
7. 无入口权限时完全隐藏按钮。

现有菜单配置遗漏 `supervisor` 列：

```text
frontend/src/views/system/MenuPermissionConfig.vue:21-64
```

不建议把 ERP 的 117 个权限继续塞入普通栏目配置，应新增正式跨应用权限管理页面。

主项目仍有多处文件预览和下载使用 URL 长效 Token，例如：

```text
frontend/src/components/business/PdfPreview.vue:121
frontend/src/api/export.js:126
frontend/src/api/notice.js:134
frontend/src/views/notice/NoticeList.vue:922
```

这不阻塞 ERP 一次性 Code 接入，但属于主项目自身待治理安全项；ERP SSO 不得沿用该模式。
