# 企微未绑定主账号审批策略

## 结论

ERP 的企微合同、付款、报销审批统一使用 `employees.wechat_userid -> employees.user_id` 识别主账号。环境变量 `WECHAT_UNBOUND_APPROVAL_POLICY` 控制申请人未绑定时的处理方式：

- `reject`：默认且生产推荐策略。三类审批均在写数据库、创建客户/供应商、执行付款联动等副作用之前拒绝，错误码固定为 `WECHAT_APPROVAL_APPLYER_UNBOUND`。
- `allow_unowned`：兼容策略。允许写入 `created_by=NULL`；报销同时写入 `user_id=NULL`。无属主记录不能可靠执行 `self/team` 数据范围，只应由具有 `all` 范围的人员处理。

未配置或配置非法值时，运行时一律按 `reject` 执行。生产启动和统一认证预检还要求显式配置合法值，避免部署时依赖隐式默认值。

## 决策责任

是否将生产策略从 `reject` 放开为 `allow_unowned`，由业务负责人决定，不由 ERP 开发团队自行决定。业务负责人需要明确接受以下影响：

1. 无属主单据无法纳入申请人本人或团队的数据范围。
2. 审计、员工维度报表、报销人追溯可能不完整，需要后续人工补绑和重放。
3. 付款或报销确认后可能影响账户余额，必须指定无属主单据的人工复核责任人。

未获得明确批准时，部署值保持：

```dotenv
WECHAT_UNBOUND_APPROVAL_POLICY=reject
```

## 放开前置条件

如业务负责人批准 `allow_unowned`，上线前必须完成：

1. 将存量数据库 `expenses.user_id` 调整为允许 `NULL`；新库初始化脚本已经按可空字段定义。
2. 验证拥有 `all` 范围的指定人员能够查询、补绑并复核无属主记录。
3. 建立未绑定告警和补绑时限，完成员工绑定后按原 `sp_no` 重放审批。
4. 在测试环境分别验证合同、付款、报销，并保留业务批准记录。

存量数据库变更由数据库负责人审核后单独执行，不在应用启动时自动修改：

```sql
ALTER TABLE expenses
  MODIFY COLUMN user_id INT NULL COMMENT '报销人（主项目 users.id；仅兼容策略允许 NULL）';
```

## 上线验收

- 生产环境模板显式设置 `WECHAT_UNBOUND_APPROVAL_POLICY=reject`。
- `npm run preflight:unified-auth` 能拦截缺失值和非法值。
- 未绑定申请人的合同、付款、报销均返回 HTTP 409 和 `WECHAT_APPROVAL_APPLYER_UNBOUND`，且无业务写入或资金副作用。
- 已绑定员工原有创建、更新、确认和资金联动流程保持不变。
